## 1. AI 코딩 지침 기본 원칙

AI는 펌웨어 코드를 생성하거나 수정할 때 다음 원칙을 우선 적용한다.

| 우선순위 | 원칙 | AI 적용 지침 |
|---:|---|---|
| 1 | 안정성 | 동작은 단순하고 예측 가능해야 하며, 잠재 버그 가능성이 있는 표현을 피한다. |
| 2 | 명확성 | 암시적 변환, 모호한 변수명, 복잡한 연산식을 피한다. |
| 3 | 이식성 | MCU, 컴파일러, 빌드 환경 차이에 영향을 덜 받도록 작성한다. |
| 4 | 유지보수성 | 함수는 작게 나누고, 동일한 패턴을 반복하지 않는다. |
| 5 | 팀 규칙 준수 | 파일명, 함수명, 자료형, 주석, Git 절차는 본 문서 기준을 따른다. |

### 1.1 AI가 반드시 따라야 할 작성 방식

- C 코드는 팀 코딩 규칙을 우선 적용한다.
- C 코드는 가능하면 ANSI C 기반으로 작성한다.
- MCU 간 자료형 크기 차이를 고려하여 `stdint.h`의 고정폭 자료형을 사용한다.
- 코드가 복잡해지면 주석으로 설명하지 말고 함수로 분리한다.
- 하나의 함수는 공백 포함 200줄 미만을 목표로 한다.
- 함수 파라미터는 최대 5개까지 사용한다.
- 6개 이상이 필요한 경우 구조체로 묶는다.
- ISR, RTOS Task, Callback, Timer Handler는 재진입성과 동시성 문제를 고려한다.
- GitLab 절차와 브랜치 흐름은 본 문서의 절차를 따른다.

### 1.2 AI가 피해야 할 작성 방식

- `int` 중심의 자료형 사용
- 경로가 포함된 `#include`
- 중괄호 없는 `if`, `for`, `while`, `switch`
- 이중 대입
- 과도하게 긴 함수
- 의미 없는 주석
- 전역 변수 남용
- ISR 내부에서 긴 처리, blocking 함수, 동적 메모리 할당 사용
- dev 브랜치 직접 push 전제로 한 안내
- PLM 등록 전 HEX 배포 전제로 한 안내

## 4. C 펌웨어 코딩 규칙

### 4.1 파일명 규칙

파일 이름은 소문자로 시작하고 `snake_case`를 사용한다.

| 파일 종류 | 약자 | 예시 |
|---|---:|---|
| Application | `a` | `a_timer.c`, `a_timer.h` |
| Driver | `d` | `d_i2c.c`, `d_i2c.h` |
| Module | `m` | `m_modbus.c`, `m_modbus.h` |

#### AI 지침

- 파일명은 `파일종류_기능명.c`, `파일종류_기능명.h` 형식으로 생성한다.
- 서로 다른 디렉터리라도 파일명 중복을 피한다.
- 파일명에는 언더바 `_` 외의 특수문자를 사용하지 않는다.

### 4.2 소스 파일 구조

AI가 C 소스 파일을 생성할 때는 아래 순서를 따른다.

| 순서 | 구역 |
|---:|---|
| 1 | 파일 헤딩 주석 |
| 2 | 헤더 인클루딩 |
| 3 | 매크로 정의 |
| 4 | 자료형 정의 |
| 5 | 함수 선언 |
| 6 | 전역 변수 및 외부 전역 변수 |
| 7 | 정적 지역 변수 및 리터럴 |
| 8 | 함수 정의 |
| 9 | 지역 함수 |
| 10 | 전역 함수 |

### 4.3 헤더 파일 규칙

- 헤더 파일은 include guard를 적용한다.
- include guard 이름은 파일명을 대문자로 변환한 형식으로 작성한다.
- `#include`에는 경로를 직접 쓰지 않는다.

```c
#ifndef _D_UART_H_
#define _D_UART_H_

/* Body of header file */

#endif /* End of _D_UART_H_ */
```

#### 금지 예

```c
#include "c:\\project\\include\\d_uart.h"
#include "/usr/include/d_uart.h"
#include "include/d_uart.h"
```

#### 권장 예

```c
#include "d_uart.h"
```

## 5. 주석 규칙

### 5.1 기본 원칙

| 구분 | 규칙 |
|---|---|
| 위치 | 코드와 주석이 섞여 가독성을 해치지 않도록 정렬한다. |
| 목적 | 코드가 무엇을 하는지보다 왜 그렇게 작성했는지 설명한다. |
| 복잡한 코드 | 주석을 추가하기보다 함수를 분리한다. |
| 비활성화 | 여러 줄 코드는 `/* */` 대신 `#if 0 ~ #endif`를 사용한다. |

### 5.2 AI 지침

- 단순 동작 설명 주석은 최소화한다.
- 하드웨어 제약, 타이밍 제약, 예외 처리 이유는 주석으로 남긴다.
- 코드 비활성화가 필요한 경우 `#if 0`을 사용한다.
- 한 줄 임시 비활성화에는 `//` 사용을 허용한다.

## 6. 자료형 규칙

### 6.1 고정폭 자료형 사용

MCU나 컴파일러마다 기본 자료형 크기가 다를 수 있으므로 `stdint.h`를 사용한다.

| 목적 | 자료형 |
|---|---|
| 부호 없는 8비트 | `uint8_t` |
| 부호 있는 8비트 | `int8_t` |
| 부호 없는 16비트 | `uint16_t` |
| 부호 있는 16비트 | `int16_t` |
| 부호 없는 32비트 | `uint32_t` |
| 부호 있는 32비트 | `int32_t` |
| 부호 없는 64비트 | `uint64_t` |
| 부호 있는 64비트 | `int64_t` |
| 32비트 부동소수점 | `float32_t` |
| 64비트 부동소수점 | `float64_t` |

> `float32_t`, `float64_t`는 프로젝트 또는 플랫폼에서 정의되어 있는지 확인 후 사용한다. 정의가 없다면 별도 typedef 또는 표준 `float`, `double` 사용 여부를 프로젝트 기준에 맞춘다.

### 6.2 구조체, 공용체, 열거형 규칙

- 구조체, 공용체, 열거형은 `typedef`로 자료형화한다.
- 태그 이름을 반드시 사용한다.
- 태그 이름 끝에는 종류를 붙인다.
  - 구조체: `_struct`
  - 공용체: `_union`
  - 열거형: `_enum`
- 타입 이름 끝에는 유형 약어와 `t`를 붙인다.
  - 구조체: `_st`
  - 공용체: `_ut`
  - 열거형: `_et`

## 8. 함수 작성 규칙

### 8.1 함수명 규칙

| 함수 종류 | 표기 방식 | 예시 |
|---|---|---|
| 지역 함수 | `snake_case` | `spi_data_write()`, `i2c_read()` |
| 전역 함수 | `CamelCase` | `SPICommandSend()`, `I2CDataWrite()` |

### 8.2 함수 설계 규칙

- 함수명은 `모듈이름_오브젝트_동작` 또는 `모듈이름_동작` 형태로 작성한다.
- 함수 파라미터는 최대 5개로 제한한다.
- 파라미터가 6개 이상이면 구조체로 묶는다.
- 구조체 또는 큰 배열을 포함한 타입은 포인터 전달을 우선 고려한다.
- 함수는 공백 포함 200줄 미만으로 작성한다.
- 함수 정의 바로 앞에는 함수 설명 주석을 작성한다.
- ISR, RTOS task, callback 함수는 재진입성과 thread-safe 여부를 고려한다.

### 8.3 함수 설명문 기본 형식

```c
/*
===============================================================================
    Function:    function_name
    Parameter:   parameter list
    Return:      return type and meaning
    Description: function purpose and important constraints
===============================================================================
*/
```

## 11. 코드 리뷰 지침

### 11.1 코드 리뷰 목적

- 소프트웨어를 실행하지 않고 사람이 직접 검토하여 잠재 결함을 찾는다.
- 코드 작성자가 발견하기 어려운 결함을 제3자가 확인한다.
- 개발 단계에서 결함을 찾아 수정 비용을 낮춘다.
- 좋은 코드를 공유하여 팀 전체 역량을 높인다.

### 11.2 코드 리뷰 수행 원칙

| 항목 | 기준 |
|---|---|
| 배포 시점 | 리뷰 5일 전 권장, 최소 3일 전 배포 |
| 참석 인원 | 개발자와 팀장을 포함한 최소 4인 |
| 대상 | 모든 F/W, S/W 단위 프로젝트는 최소 1회 이상 |
| 리뷰 자료 | 설명서, Flow Chart, 검증 자료 배포 권장 |
| 종료 기준 | 리뷰어 전원 동의 후 보고서 작성 |
| 완료 기준 | 그룹웨어 기안, 원본 첨부, 팀장 결재 완료 |

### 11.3 리뷰어 코멘트 원칙

- 사람을 비판하지 않고 코드 자체를 평가한다.
- 작성자가 납득할 수 있도록 이유를 설명한다.
- 가능한 부드럽고 존중하는 표현을 사용한다.
- “왜?”라는 표현보다 “이 부분은 ~ 가능성이 있어 ~ 방식이 더 안전합니다.”처럼 작성한다.
- 수정하겠다는 답변 후 실제 수정 여부를 재확인한다.

### 11.4 코드 리뷰 필수 확인 항목

| 구분 | 확인 내용 |
|---|---|
| Coding Convention | 파일명, 함수명, 들여쓰기, 괄호, 주석 규칙 준수 여부 |
| Coding Standardization | 팀 코딩 규칙, ANSI C, 필요 시 MISRA-C 관점 검토 |
| Algorithm | 알고리즘 논리, 경계값, 예외 처리 검토 |
| Bug | NULL, overflow, race condition, ISR 처리, timeout 검토 |
| Build | STM32/TI 빌드 산출물 생성 확인 |
| Evidence | 정적분석 또는 코드 리뷰 결과 증빙 첨부 |

## 12. GitLab 소스코드 관리 지침

### 12.1 브랜치 기본 흐름

```text
main
 └── dev
      └── dev_개인브랜치명
```

### 12.2 브랜치 명명 규칙

| 브랜치 | 규칙 | 예시 |
|---|---|---|
| main | 최종 승인 브랜치 | `main` |
| dev | 개발 통합 브랜치 | `dev` |
| 개인 브랜치 | `dev_개인브랜치명` | `dev_jylee1`, `dev_jylee1_spi_debug` |

## 13. 펌웨어 빌드 산출물 관리

### 13.1 EXEC 폴더 규칙

- dev 브랜치로 머지 준비 시 산출물 파일을 생성한다.
- 산출물 파일은 `EXEC` 폴더에 넣는다.
- 압축하지 않고 직접 파일명을 변경하여 저장소에 추가한다.

### 13.2 MCU별 산출물 규칙

| 환경 | 산출물 |
|---|---|
| TI | `.out` 파일 |
| STM32 | `.hex` 파일 |
| ATMEL | `.hex` 파일 |

### 13.3 HEX 파일명 규칙

HEX 파일 이름은 PLM 자료 등록 규정을 따른다.

```text
23100098_CHPC-LON1(DUAL)-A_HEX_R01.HEX
```

### 13.4 Tag 규칙

- main 브랜치에 `Rxx` tag를 생성한다.
- `R00`부터 시작한다.
- PLM 리비전과 동일한 태그를 생성한다.
- Tag Message에는 이전 태그 대비 개정내역을 구체적으로 기록한다.
- PLM에 등록되지 않은 HEX는 배포하지 않는다.

## 14. AI 코드 생성 시 최종 점검 규칙

AI는 코드를 제안할 때 아래 기준을 함께 점검한다.

| 구분 | 점검 질문 |
|---|---|
| 파일명 | 파일명이 팀 규칙을 따르는가? |
| include | include 경로가 하드코딩되어 있지 않은가? |
| 자료형 | `stdint.h` 기반 고정폭 자료형을 사용하는가? |
| 함수 | 함수 파라미터가 5개 이하인가? |
| 함수 길이 | 함수가 200줄 미만인가? |
| 중괄호 | 조건문/반복문에 항상 중괄호가 있는가? |
| 주석 | 주석이 이유와 제약을 설명하는가? |
| 전역 변수 | 전역 변수 사용이 필요한 경우로 제한되는가? |
| ISR | ISR 내부 처리가 짧고 안전한가? |
| 동시성 | RTOS/ISR 공유 자원 보호가 고려되었는가? |
| 빌드 | STM32/TI 환경에서 산출물 규칙을 만족하는가? |
| Git | 개인 브랜치 → dev → main 흐름을 따르는가? |
